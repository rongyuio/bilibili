# 版本策略

本模块的版本号同时是 Git tag 名与 Go 模块版本号，两者必须完全一致：`go get github.com/rongyuio/bilibili@v0.4.0` 取的就是 tag `v0.4.0`。

## 版本格式

tag 必须是 `v` 开头的三段式语义化版本，即 `v<major>.<minor>.<patch>`，可在 patch 后追加预发布后缀。

| 形式 | 结果 | 说明 |
| --- | --- | --- |
| `v0.3.0`、`v1.2.3` | 允许 | 正式版本 |
| `v0.4.0-rc.1`、`v0.4.0-beta.2` | 允许 | 预发布版本，发布为 GitHub Pre-release |
| `v0.4.0+build.1` | 拒绝 | 不使用 build metadata，原因见下 |
| `v1`、`v0.3` | 拒绝 | 段数不足，不是合法的模块版本 |
| `v0.4.0.1` | 拒绝 | 段数过多 |
| `v01.2.3`、`v0.04.0` | 拒绝 | 数字段不允许前导零 |
| `0.4.0` | 拒绝 | 缺少 `v` 前缀 |

`release.yml` 用 SemVer 官方正则校验 tag 名，不符合即拒绝发布。`v1`、`v0.3` 这类连两个点都没有的 tag 甚至不会触发工作流。已发布的正式版本：`v0.1.0`、`v0.2.0`、`v0.3.0`、`v0.4.0`、`v0.5.0`。

### 不使用 build metadata

`+` 开头的 build metadata 虽然被 SemVer 允许，但不用于本模块的 tag：

- Go 比较版本时忽略 `+` 后缀，并在规范化时把它移除，因此 tag `v0.4.0+build.1` 与模块版本 `v0.4.0` 在 `go` 命令看来是同一个版本，tag 名与实际版本对不上；
- `+incompatible` 按 Go 官方说明不应出现在仓库 tag 上，本模块有 `go.mod`，也用不到它。

需要标记「正式版之前的验证构建」时用预发布后缀，不要用 build metadata。

### 预发布版本

- 后缀以 `-` 开头，由 `.` 分隔的标识符组成，字符限 ASCII 字母、数字与 `-`，例如 `v0.4.0-rc.1`；
- 排序上低于同号正式版本：`v0.4.0-rc.1` < `v0.4.0`；
- 这类 tag 会发布为 GitHub Pre-release，不会被标记为 Latest。

## 递增规则

| 变更内容 | 递增 | 示例 |
| --- | --- | --- |
| 新增接口、导出类型或字段 | minor | `v0.3.0` → `v0.4.0` |
| 缺陷修复，且不改变导出 API | patch | `v0.3.0` → `v0.3.1` |
| 破坏性变更 | 见下文 | — |
| 文档、注释或内部重构（不改导出 API） | 可累积到下一功能版本，或按 patch 发布 | — |

## v0 阶段与 v1 之后

Go 把 major 为 0 的版本视为**不稳定版本**，不受兼容性要求约束。当前处于 v0 阶段，因此：

- 破坏性变更随**次版本号**发布即可，不需要升主版本，也不需要改模块路径；
- 破坏性变更仍须在提交中用 `type!` 标注（见 [CONTRIBUTING.md](../.github/CONTRIBUTING.md)），并在[迁移指南](migration.md)中补充旧写法与新写法的对应条目。

发布 `v1.0.0` 之后再出现破坏性变更，需要升主版本，并把模块路径改为带主版本后缀的形式：

```go.mod
module github.com/rongyuio/bilibili/v2
```

调用方的导入路径同步变为 `github.com/rongyuio/bilibili/v2`。

## 最低 Go 版本

本模块要求 **Go 1.26 或更新版本**。依据是代码使用了 Go 1.26 新增的标准库 API `errors.AsType`（见 `decode_diagnostic.go`）；依赖层的要求更低——`golang.org/x/net` 与 `golang.org/x/sys` 要求 1.25——因此 1.26 是当前下限。

`go.mod` 的 `go` 指令表示**最低支持版本**，不是"当前 Go 版本"。升级它会让所有使用更旧工具链的调用方被迫升级，因此只在必要时提升：

- 需要用新的语言特性或标准库 API；
- 依赖升级后强制要求更高版本。

提升时应在同一个 PR 中说明理由，并同步更新本节与 README 的版本要求。CI 通过 `go-version-file: go.mod` 取用该版本，因此指令一改、验证环境立即跟随；反过来，若有人写入更高版本才有的代码，编译器会直接报 `requires go1.27 or later` 之类的错误，无法合入。
